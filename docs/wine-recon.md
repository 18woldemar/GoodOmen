# Разведка через Wine

Wine — это инструментированная реализация Win32. Всё, ради чего под Windows
пишут прокси-DLL, здесь включается переменной окружения. Это главное
преимущество работы под Linux в таком проекте.

## Подготовка префикса

Игра 32-битная, префикс тоже:

```bash
export MDK2_GOG="$HOME/wine/mdk2-gog"
WINEARCH=win32 WINEPREFIX="$MDK2_GOG" wineboot -i
```

Отдельный префикс на каждое издание — иначе диффы изданий бессмысленны.
На CachyOS multilib включён по умолчанию, дополнительных действий не нужно.

## 1. Какие файлы игра открывает и в каком порядке

Самый дешёвый и самый информативный трейс. Отвечает на вопрос «что вообще
грузится при старте уровня» до всякого анализа форматов.

```bash
WINEPREFIX="$MDK2_GOG" WINEDEBUG=+file wine MDK2.exe 2> trace-file.log
```

Порядок открытия задаёт граф зависимостей: контейнер → индекс → ресурсы.
Файл, который открывается первым, почти всегда оглавление.

Полезно сопоставить с `+relay` (полный трейс вызовов Win32), но он на
порядок объёмнее — включать только на короткий сценарий:

```bash
WINEDEBUG=+relay wine MDK2.exe 2> trace-relay.log   # десятки МБ в секунду
```

Сузить относительно шума можно через `HKCU\Software\Wine\Debug`, ключи
`RelayInclude` / `RelayExclude`.

## 2. Что реально уходит в GPU

Wine транслирует Direct3D 7 в OpenGL (wined3d). Значит GL-поток можно
записать `apitrace` и посмотреть **настоящие вершинные и индексные буферы**
игры — с координатами, UV, нормалями и порядком треугольников.

```bash
apitrace trace --api gl -- wine MDK2.exe
qapitrace MDK2.exe.trace     # GUI: покадрово, с содержимым буферов
```

Это самый сильный тест на M3–M4: то, что вытащил наш парсер из `.mdl`,
должно совпадать с тем, что оригинал отправил в GL. Расхождение сразу
показывает, где ошибка — в раскладке вершины, в порядке индексов или в
матрице трансформации.

Уровень детализации D3D-слоя:

```bash
WINEDEBUG=+d3d,+d3d_draw,+d3d_shader,+ddraw wine MDK2.exe 2> trace-d3d.log
```

Альтернативный маршрут, если wined3d что-то ломает: dgVoodoo2
(D3D7 → D3D11) поверх DXVK (D3D11 → Vulkan), захват RenderDoc. Сложнее в
настройке, но даёт полноценные кадровые снимки.

## 3. Звук и ввод

```bash
WINEDEBUG=+dsound wine MDK2.exe 2> trace-snd.log     # форматы буферов, частоты
WINEDEBUG=+dinput wine MDK2.exe 2> trace-input.log
```

Параметры звуковых буферов дают формат аудиоресурсов почти напрямую:
частота, битность, каналы — без разбора заголовков.

## 4. Отладчик

```bash
WINEPREFIX="$MDK2_GOG" winedbg MDK2.exe
WINEPREFIX="$MDK2_GOG" winedbg --gdb MDK2.exe   # дальше обычный gdb
```

Типовой приём: поставить брейкпоинт на `ReadFile`, посмотреть, в какой
буфер и сколько байт читается, затем — куда этот буфер уходит. Так
находится функция-парсер формата, а от неё уже пляшет анализ в Ghidra.

## 5. Дамп памяти

Когда формат в файле сжат, а в памяти лежит развёрнутым, проще снять
распакованное представление:

```bash
# найти pid запущенной игры
pgrep -f MDK2.exe
# дальше — winedbg, либо чтение /proc/PID/mem по картам из /proc/PID/maps
```

## Пакеты

```bash
sudo pacman -S wine winetricks apitrace renderdoc rizin rizin-cutter \
               python-pillow python-numpy
yay -S ghidra imhex python-pefile python-kaitaistruct
```

Названия в AUR со временем меняются — если пакет не найден, искать по
имени инструмента. Ghidra требует JDK; на Arch ставится как зависимость.

## Порядок на M0

1. `+file` трейс старта и загрузки первого уровня → список ресурсов.
2. `exe_recon.py` на GOG-овском exe → API, тулчейн, RTTI, расширения.
3. `inventory.py` по всем трём установкам.
4. `diffsets.py` GOG vs 1С → где сидят строки.
5. Свести в `docs/journal.md`: какие форматы существуют, какой брать первым.
